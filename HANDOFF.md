## Повторный аудит (2-й проход) — что найдено и исправлено

Исправлено (все с тестами или проверкой в браузере):

- **Play после ошибки потока ничего не делал** (`audio.play()` на элементе с
  фатальной ошибкой не перезапускает загрузку), восстановиться можно было только
  сменой канала. Теперь `resume()` вызывает `audio.load()`, если у элемента есть
  `error`. Подтверждено на старом и новом коде в Chromium.
- **После долгой паузы воспроизводился устаревший буфер живого потока.** Если
  пауза дольше 15 с, `resume()` перезагружает поток (`STALE_AFTER_PAUSE_MS`).
- **Ответы API не проверялись:** `channels.json` без списка или `songs.json` не
  массивом ломали `.length` позже. Теперь `api.getChannels`/`getChannelSongs`
  валидируют форму и отбрасывают некорректные записи (`isChannel`, `isSong`;
  кэш каналов использует тот же `isChannel`).
- **Возврат на играющий канал во время загрузки другого** игнорировался, и
  загружавшийся канал всё равно включался. Теперь отложенное переключение
  отменяется.
- **Нет обратной связи при смене канала:** `channelLoading` нигде не показывался.
  Добавлено «Loading channel…».
- **Визуализатор:** потолок ~60 кадров/с (на 120/144 Гц экранах анимация шла
  в 2+ раза быстрее и жгла CPU), цикл отрисовки останавливается на паузе
  (после ~3 с) и возобновляется на `play`; размер холста меняется шагом 64 px
  при ресайзе окна (меньше реаллокаций).
- **`AppImage`:** удалена неиспользуемая ветка локальных картинок
  (`new URL('../assets/images/${src}')`), из-за которой Vite клал в `dist` весь
  каталог изображений, включая `player-screenshot.jpg` (368 КБ). Теперь
  рисуются только `https://` (http upgrade), остальное, включая `data:`/`javascript:`,
  заменяется заглушкой.
- **Доступность:** `alt=""` у декоративных картинок каналов (раньше читался id
  канала), `aria-expanded` у кнопки списка каналов. Убран `id` на `<li>` из данных
  API (нигде не использовался; потенциальный DOM clobbering).

Сделано после этого (по предложениям второго прохода):

- **Автопереподключение** (`usePlayer`): при обрыве потока до 3 повторов с паузами
  1 с, 2 с, 4 с («Connection lost. Reconnecting…»), затем итоговая ошибка. Сбрасывается
  при успешном `playing`, смене канала, паузе пользователя и размонтировании.
  Отклонённый `play()` с `NotSupportedError` больше не затирает сообщение (за ошибки
  загрузки отвечает событие `error`). Проверено в Chromium: поток, упавший дважды,
  восстанавливается сам; постоянно падающий — 1 + 3 запроса и итоговая ошибка.
- **Тип `Channel`** разделён: `ChannelSummary` (элемент `channels.json`, без песен) и
  `Channel extends ChannelSummary` (с `songs`); `Song` вынесен отдельно.
- **Прелоадер** без искусственной задержки 500 мс.

Сделано по отзыву с реального SomaFM (`ERR_CONNECTION_RESET` посреди воспроизведения,
плеер оставался в состоянии «играет» без сообщений):

- **Корень проблемы.** При сбросе соединения посреди потока Chromium НЕ шлёт `error`
  и `ended`: только `waiting`, потом `stalled`; `paused` остаётся `false`, `currentTime`
  стоит (воспроизведено на локальном «живом» WAV-сервере). Прежняя логика реагировала
  только на `error`.
- **`usePlayer` переписан как автомат состояний** (`connecting | playing | buffering |
  reconnecting | paused | failed`): статус-текст «Connecting…» / «Buffering…» /
  «Connection lost. Reconnecting… (n of 3)», после 3 неудачных попыток итоговая
  ошибка и кнопка Play. **Сторож** по `currentTime` (нет прогресса 6 с при
  игре/буферизации или 10 с при подключении = соединение потеряно) ловит тихие
  обрывы; `ended` тоже считается потерей связи (живой поток не заканчивается).
  Проверено в Chromium: «мёртвый» поток даёт 1 + 3 запроса и итоговое сообщение;
  поток, зависший без событий, переподключается сам.
- **Без щелчков при переключении звука.** Весь звук идёт через `GainNode`
  (`src/lib/audio-output.ts`, общий для плеера и визуализатора): громкость, mute,
  пауза и смена канала сглаживаются (постоянная 15 мс); пауза и смена `src` делаются
  через 60 мс после затухания; звук нарастает на `playing`. `audio.volume` теперь
  всегда 1. Без Web Audio остаётся прежнее поведение (громкость элемента).

Сделано по следующим просьбам:

- **Запоминание последнего канала** (`localStorage`, ключ `somafm-player:last-channel`).
  После перезагрузки канал подготавливается без автозапуска (браузеры блокируют
  автоплей без жеста): название, описание, песня, подсветка и прокрутка к нему в списке;
  к потоку нет ни одного запроса до нажатия Play (`preload="none"`). Выбор другого
  канала снова автозапускается (`store.autoplay`). Неизвестный/недоступный сохранённый
  канал игнорируется молча. Восстановление не блокирует показ списка (кэш каналов
  показывается сразу, канал подгружается в фоне).
- **Опрос смены трека** (`src/composables/song-refresh.ts`): у SomaFM нет push-канала,
  поэтому остаётся опрос `songs/<id>.json` раз в 15 с, но теперь только пока звук
  нужен (не на паузе) и вкладка видна, с мгновенным обновлением при Play, возврате на
  вкладку и переподключении (раньше до следующего тика показывался старый трек) и без
  дубль-запроса сразу после загрузки канала (`store.songsUpdatedAt`).

Идеи по смене трека, если 15 с мало (нужно ваше решение):

1. Интервал опроса 10 с (или 5 с) — тривиально (`SONGS_REFRESH_INTERVAL_MS`), но это
   нагрузка на бесплатный сервис SomaFM; точное время конца трека API не даёт
   (в `songs.json` только время начала), поэтому «умный» опрос только по длительности
   не гарантирует меньшую задержку.
2. Метаданные внутри потока (ICY, заголовок `Icy-MetaData: 1`): точное название без
   опроса и в такт звуку. Но `<audio>` их не отдаёт: нужен свой читатель потока
   (`fetch` + разбор блоков `icy-metaint`) и свой декодер/воспроизведение
   (MSE / Web Audio), плюс CORS на заголовок `Icy-MetaData` и экспозиция
   `icy-metaint` на стрим-серверах SomaFM (не проверено). Крупная переделка плеера,
   на Safari/iOS MSE ограничен. Имеет смысл только после проверки CORS на реальных
   стримах.

## Проверка на реальном SomaFM (из сессии с открытым доступом к хостам SomaFM)

Подтверждено на настоящих ответах (`api.somafm.com`, плейлисты, ответ `ice*.somafm.com`
на CORS preflight):

- `channels.json`: 51 канал, **все проходят** проверку `isChannelSummary`; плейлисты
  (`mp3/highest`, `aac/highest`, `aacp/high`, `aacp/low`) и картинки только на
  `https://api.somafm.com`.
- `.pls` отдаёт CORS (`Access-Control-Allow-Origin: *`) и **4 зеркала** потока
  (`File1..File4`), напр. `ice4/ice6/ice2/ice5.somafm.com`, всегда `https`, без портов
  и без редиректов. Допущение `TRUSTED_HOST = *.somafm.com` верно; проблемы с
  `http://`-портами нет.
- `songs/<id>.json`: поле называется `albumArt` (не `albumart`; тип исправлен),
  `date` = Unix-время начала трека в секундах (строка).
- CSP сужена по этим данным: `img-src 'self' data: https://api.somafm.com`,
  `media-src https://*.somafm.com`. Если SomaFM добавит другие хосты (CDN), расширить.
- Icecast SomaFM (`Icecast 2.4.0-kh22-Soma1.7`) на preflight с `Icy-MetaData`
  отвечает 204 с `Access-Control-Allow-Headers: *` и
  `Access-Control-Expose-Headers: ... Icy-MetaInt ...`, то есть **браузер может запросить
  ICY-метаданные и прочитать `icy-metaint`**. Не проверено: что блоки метаданных
  реально содержат `StreamTitle` и совпадают по времени со звуком (запрос потока из
  этой среды с нестандартным User-Agent делать не следует, см. ниже).
- Серверы потоков отвечают `403` на стандартный User-Agent `curl` (фильтр не-браузерных
  клиентов): серверное/скриптовое чтение потоков не вариант, только браузер.

**Результат у владельца (реальный браузер):** запрос `fetch` с `Icy-MetaData: 1` к
`ice4.somafm.com` получает `403 (Forbidden)` (в консоли `net::ERR_ABORTED 403`), хотя
обычный `<audio>` тот же адрес играет. Из этой среды воспроизвести нельзя (серверы потоков
отвечают 403 и настоящему headless-Chromium, и `<audio>`; сеть/UA другие). Страница
`tools/icy-probe.html` теперь явно сообщает HTTP-статус и имеет кнопку «Диагностика»
(таблица: fetch без заголовков / с `Icy-MetaData` / с `Range` / оба + контрольный
`<audio>`), чтобы увидеть, какой заголовок отклоняется. Если 403 только у вариантов с
`Icy-MetaData`, чтение метаданных из браузера у SomaFM **невозможно** (серверы отклоняют
такие запросы), и вариант ICY закрывается.

**Выяснено позже:** 403 на потоки на `localhost` вызывает заголовок `Referer: http://localhost:3000/`
(на Vercel и при открытии адреса прямо во вкладке, где `Referer` нет, звук играет; проверки
`crossOrigin`/`referrerPolicy` из консоли были некорректны: у `<audio>` нет атрибута
`referrerpolicy`). Лечение: `<meta name="referrer" content="no-referrer">` в `index.html` и
`Referrer-Policy: no-referrer` в `vercel.json`. Поэтому предыдущий вывод про `Icy-MetaData` и
403 был ложным: 403 получал любой запрос с localhost; ICY нужно перепроверить после
этой правки (`tools/icy-probe.html`: `fetch` тоже отправляет `Referer`, теперь без него).

**ICY работает (проверено владельцем):** после правки `Referer` страница `tools/icy-probe.html`
показала ✅ с реальными названиями треков (меняются прямо в потоке). Выбран путь «C»: собственный
плеер на MSE с откатом на `<audio>`; план в `docs/icy-mse-plan.md`; браузеры: Chrome и Firefox (iPhone
необязателен); опрос API при живом ICY отключать. Этап 0 (спайк) в Chrome пройден (17 мин, без ошибок), Firefox ждёт проверки. Сделаны
этап 1 (`src/lib/icy-demuxer.ts`) и этап 2 (`src/lib/mse-stream.ts`), оба с тестами и пока не подключены
к приложению; этап 3 тоже сделан (транспорт в `usePlayer`: `?transport=mse` включает MSE, по умолчанию прежний
`<audio src>`, откат per-channel); этап 4 тоже сделан (название из потока показывается в интерфейсе и Media Session, опрос API отключён при живом
ICY); этап 5 сделан: MSE включён по умолчанию для всех браузеров со стандартным `MediaSource` + `audio/mpeg`
(выключатель `?transport=audio`, откат на `<audio>` per-channel при любом провале MSE до первого звука);
Firefox владелец ещё не проверял, iPhone остаётся на `<audio>`.

**Как проверить ICY у себя:** `npm run dev`, открыть
`http://localhost:3000/tools/icy-probe.html`, нажать «Проверить». Страница читает поток
с `Icy-MetaData: 1`, показывает заголовки ответа, блоки метаданных, найденные названия
треков и возможности браузера для собственного плеера (MSE, WebCodecs, iOS). Итог
(✅/⚠️/❌) пояснит, можно ли получать название трека из потока. Логика страницы
отлажена на локальном ICY-сервере в 4 вариантах CORS.

**Резервные зеркала** (сделано): `api.getStreamUrls` отдаёт все проверенные адреса из
`.pls` (порядок сохраняется, дубли и чужие хосты отбрасываются), store хранит
`streamUrls`, а `usePlayer` владеет `src` элемента: первый адрес ставится сразу, при каждом
переподключении берётся следующее зеркало **по кругу** (после последнего снова первое),
после 3 неудач (4 сервера успеют перебраться) нажатие Play начинает с первого,
возобновление после ошибки media берёт следующее, после долгой паузы то же самое зеркало.
Смена канала подменяет `src` только после затухания звука (60 мс). Проверено в
Chromium: два мёртвых зеркала подряд, затем рабочее — звук возвращается сам;
все четыре мёртвые — по одному запросу к каждому и итоговое сообщение.
